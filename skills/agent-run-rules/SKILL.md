# Agent 运行规范

## 启动前检查

每次开始处理任务前，先完成这些动作：

1. 阅读本文件，确认当前任务应遵循的流程和限制。
2. 检查当前目录、分支、远程仓库和工作区状态。
3. 识别已有用户改动，不覆盖、不回滚、不顺手重构无关内容。
4. 判断任务是否需要联网、安装依赖、访问远程仓库、运行长任务或执行潜在破坏性命令。
5. 若任务涉及代码变更，先从最新 `main` 创建独立分支。

默认工作目录为项目根目录。除非用户明确要求，不要在项目外创建或修改文件。

## 沟通规范

使用中文与用户沟通，保持简洁、明确、可执行。

在以下节点给用户短更新：

- 开始读取上下文时。
- 准备修改文件前。
- 运行关键验证前。
- 遇到权限、网络、依赖、认证或数据风险时。
- 完成提交、推送或 PR 后。

不要把工具输出原样堆给用户。最终回复只总结关键结果、文件位置、验证情况和剩余风险。

## Git 流程

所有代码、文档和配置变更都必须遵循分支与 PR 流程：

1. 在动手前运行 `git status --short --branch`。
2. 确认 `main` 与远端同步；若可联网，先拉取远端最新状态。
3. 从 `main` 创建语义清晰的分支，例如 `feature/add-qmt-gateway-api`、`fix/history-cache-bug`、`docs/update-runbook`。
4. 每次出现变更后，都要同步更新根目录 `CHANGELOG.md`，记录日期、变更类型、摘要和验证情况。
5. 每次提交只包含与当前任务直接相关的文件。
6. 提交信息使用简洁英文 Conventional Commit 风格，例如 `feat: add market snapshot api`。
7. 推送功能分支到远端。
8. 创建 PR，PR 描述包含变更摘要、验证结果和风险说明。

除仓库初始化、远端修复等维护动作外，不要直接向 `main` 推送功能变更。

如果本次只有文档、说明、规范或注释类变更，暂时不要推送分支，也不要创建或更新 PR；在本地完成变更和 `CHANGELOG.md` 记录后等待后续代码变更，再与代码变更一并推送并提交 PR。若用户明确要求立即推送文档变更，以用户最新指令为准。

## 文件与编码

所有新建文本文件默认使用 UTF-8 编码。

中文内容直接保存为 UTF-8，不使用 GBK、ANSI 或转义形式替代正文。命令行显示乱码时，不要据此判断文件内容损坏；优先检查文件字节、编辑器编码或 Git diff。

遵循以下原则：

- 不提交密钥、token、账号、cookie、证书、`.env` 或本地授权文件。
- 不提交 QMT 本地数据、缓存、数据库、日志、回测结果和大型二进制数据。
- 不在无关文件中做格式化、换行风格或编码批量变更。
- 新增文件路径和命名保持清晰、可搜索、可维护。

## 代码修改

修改代码前先理解现有结构、依赖和调用路径。

优先采用项目已有风格和工具链；没有明确模式时，选择简单、可测试、可维护的实现。避免过早抽象，避免把当前任务扩展成无关重构。

所有代码文件首行必须使用中文简短介绍该文件功能。Python 文件使用 `# ...` 注释，PowerShell 文件使用 `# ...` 注释；保留原有模块 docstring、shebang 或其他内容时，也要确保中文功能说明位于文件第一行。

若任务涉及 QMT、xtquant 或交易能力，默认采用保守策略：

- 先只读，后写入。
- 先内网，后公网。
- 先数据接口，后交易接口。
- 先明确状态与错误，再做自动化恢复。
- 交易相关功能必须包含鉴权、幂等、风控、审计和熔断设计。

## 命令与安全

运行命令前判断风险。涉及以下行为时必须谨慎，并按权限要求请求用户批准：

- 推送远端、创建 PR、安装依赖或访问网络。
- 删除、移动、覆盖大量文件。
- 修改项目外文件。
- 启动 GUI 程序、系统服务、计划任务或后台常驻进程。
- 执行可能影响 QMT、交易账户、真实订单或生产数据的操作。

不要使用破坏性 Git 命令回滚用户改动，例如 `git reset --hard`、`git checkout -- <file>`，除非用户明确要求。

## 验证标准

完成变更后，根据任务风险选择验证方式：

- 文档或 skill 变更：检查格式、编码、链接和 Git diff。
- Python 代码：优先运行相关单元测试、语法检查或最小导入验证。
- API 服务：验证启动、健康检查、核心接口和错误路径。
- 数据处理：验证样例输入、边界条件、缓存命中和缺失数据行为。
- 交易相关：默认只做模拟、只读或 dry-run 验证，禁止未经确认触发真实下单。

若无法运行某项验证，在最终回复中明确说明原因和残余风险。

## PR 描述模板

创建 PR 时使用以下结构：

```markdown
## Summary
-

## Validation
-

## Risk
-
```

如果变更涉及接口、数据格式、配置、迁移或运行方式，在 PR 中额外说明兼容性影响。

## 完成前检查

结束任务前确认：

1. 工作区状态符合预期。
2. 变更文件与任务范围一致。
3. `CHANGELOG.md` 已记录本次变更，或已说明为什么不需要记录。
4. 敏感信息和大数据没有进入 Git。
5. 必要验证已运行或已说明不能运行。
6. 若包含代码变更，分支已推送，并已创建或准备创建 PR。
7. 若仅包含文档变更，已按规则暂不推送，并在最终回复中说明本地提交状态。
8. 最终回复包含分支、提交、PR 链接或下一步阻塞点。
